TELECOM SOFT Academy — как разместим сайт на Vercel и базу в Neon
Дата проверки инструкции: 21.10.2026

СХЕМА
GitHub хранит код → Vercel публикует сайт и выполняет API → Neon хранит данные.
Word, PDF и материалы ВКР остаются отдельно на компьютере.

ТЕКУЩИЙ СТАТУС
Сайт 0.2 работает локально на Node.js и SQLite. PostgreSQL ещё не подключён,
обработчик Vercel и vercel.json ещё не созданы. Публикации пока нет.
Инструкция описывает наш следующий этап, а не уже выполненное размещение.

1. ЧТО ПОНАДОБИТСЯ ОТ ТЕБЯ

Создать или открыть личные аккаунты:
• GitHub: https://github.com — исходники сайта.
• Vercel: https://vercel.com — сайт и API. Удобно войти через тот же GitHub.
• Neon: https://console.neon.tech — PostgreSQL.

Для личной некоммерческой демонстрации дипломного проекта рассматриваем Vercel
Hobby и Neon Free. У тарифов есть лимиты; точные квоты смотрим в панели при
создании. Если платформа станет рабочим корпоративным сервисом TELECOM SOFT,
условия Vercel Hobby для такого использования не подходят — тариф пересмотрим.
Собственный платный домен для первой публикации не нужен: используем адрес Vercel.
Пароли аккаунтов и строку подключения к БД в переписку присылать не требуется.

2. ЧТО Я ПОДГОТОВЛЮ ДО ПУБЛИКАЦИИ

• Сохраню рабочую локальную версию и согласованную резервную копию SQLite.
• Перенесу схему 12 таблиц на PostgreSQL, переделаю запросы и транзакции.
• Подготовлю отдельные операции создания схемы и переноса учебных данных.
  База не должна пересоздаваться или заполняться при каждом открытии сайта.
• Сохраню пользователей, хеши паролей, курсы, прогресс, заметки и практические
  работы. Действующие локальные сессии переносить не требуется: войдём заново.
• Подготовлю API для Vercel, маршруты, vercel.json и пример переменных окружения.
• Настрою HTTPS, cookie, проверку Origin и ограничение попыток входа с учётом
  нескольких экземпляров функции.
• Проверю прежние 34 сценария на PostgreSQL и сверю перенесённые записи.

Почему этот этап обязателен: Vercel Functions не предоставляют постоянный
локальный диск для изменяемой SQLite-базы. Загрузка academy.sqlite в Neon
тоже не переносит данные: Neon работает с PostgreSQL.
Источник: https://vercel.com/docs/functions/runtimes

Сейчас не нужно запускать «npm run db:migrate» или «npm run build»:
таких команд в текущем package.json нет. Точные команды переноса и параметры
сборки я добавлю вместе с подготовленной версией кода.

3. СОЗДАЁМ БАЗУ В NEON

1) Открыть Neon Console и создать проект, например telecom-soft-academy.
2) Выбрать Free. Регион базы согласуем с регионом функции Vercel, чтобы запросы
   не ходили между далёкими регионами. Итоговый выбор проверим в обеих панелях.
3) Оставить созданную базу и записать её название. Если предлагается neondb,
   это нормальное название — переименовывать ради инструкции не обязательно.
4) Нажать Connect, выбрать нужную ветку, базу и роль.
5) Включить Connection pooling и скопировать полную строку подключения.
   Она начинается с postgresql://; у pooled-адреса обычно есть -pooler.
   Все параметры TLS из выданной строки оставить без изменений.

Эту строку используем как DATABASE_URL серверной части. Для миграций и
резервного копирования отдельно возьмём direct connection из того же окна,
если выбранному инструменту нужно прямое соединение. Пароль не публикуем.
Источник: https://neon.com/docs/connect/connection-pooling

Далее я выполню подготовленный перенос в новую базу и проверю количество
записей, связи, вход и сохранение прогресса. Исходный SQLite-файл сохраним.
Не запускаем повторный импорт поверх заполненной базы без проверки его режима.

4. ЗАГРУЖАЕМ КОД НА GITHUB

Создадим репозиторий telecom-soft-academy в личном аккаунте GitHub.
Можно выбрать Private. Для бесплатного сценария Vercel используем личный
репозиторий, а не приватный репозиторий организации.

В корне репозитория будут лежать файлы подготовленной папки site:
package.json, lock-файл, серверные модули, public, обработчик API,
vercel.json и файлы миграций. То есть package.json находится сразу в корне.

Не загружаем: data/, academy.sqlite и его служебные файлы, node_modules/,
test-results/, .env и другие файлы с секретами, резервные копии, Word/PDF ВКР.
Перед первым коммитом расширю .gitignore и проверю список отправляемых файлов.
Текущий .gitignore уже исключает data/, node_modules/, test-results/ и .env.

Если выберем загрузку всего проекта вместо отдельного репозитория сайта,
Root Directory в Vercel придётся изменить. В этой инструкции используем
один понятный вариант: содержимое site — корень отдельного репозитория.

5. ПОДКЛЮЧАЕМ VERCEL

Этот шаг выполняем после подготовки кода и заполнения Neon.

1) Vercel Dashboard → Add New / New Project.
2) Подключить GitHub и разрешить доступ к репозиторию telecom-soft-academy.
3) Нажать Import напротив нужного репозитория.
4) Проверить имя проекта и Root Directory: корень репозитория.
5) Для текущего приложения без фреймворка ориентир — Framework Preset: Other.
   Окончательные Build / Output Settings возьмём из подготовленной конфигурации.
   Не вписываем команды наугад и не загружаем одну папку public:
   без серверной части не будут работать вход и сохранение данных.
6) Добавить переменные окружения из следующего пункта, затем нажать Deploy.

Назначенный постоянный адрес проверим в Settings → Domains. Если его ещё нет
при первоначальном импорте, после появления адреса внесём PUBLIC_ORIGIN и
выполним Redeploy. До этого первую публикацию не считаем готовой к проверке входа.
Источник: https://vercel.com/docs/git

6. ПЕРЕМЕННЫЕ ОКРУЖЕНИЯ VERCEL

Project → Settings → Environment Variables. Для первого рабочего запуска
настраиваем Production. Секреты вводим через панель, без кавычек вокруг значения.

DATABASE_URL
  Полная pooled-строка подключения из Neon. Это секрет серверной части.

PUBLIC_ORIGIN
  Постоянный HTTPS-адрес сайта, например https://ИМЯ-ПРОЕКТА.vercel.app
  Пример — шаблон, его нельзя копировать буквально. Указываем реальный домен
  без пути, без / в конце. Он нужен для проверки запросов с сайта.

COOKIE_SECURE
  Значение: 1. В опубликованной версии cookie сессии отправляется через HTTPS.

DB_PATH для подключения Neon не используется. DATABASE_URL не помещаем
в public/, JavaScript браузера, подписи скриншотов или NEXT_PUBLIC_*.

После изменения переменных нужен новый deployment / Redeploy:
уже опубликованная сборка автоматически новые значения не получает.
Источники:
https://neon.com/docs/guides/vercel-manual
https://vercel.com/docs/environment-variables

Preview-версии настроим отдельно: своя тестовая ветка/база Neon и подходящий
Origin. Production-адрес в PUBLIC_ORIGIN не подходит случайным Preview-доменам.
Первую проверку проводим по постоянному Production-домену из Settings → Domains.

7. ПРОВЕРЯЕМ ОПУБЛИКОВАННЫЙ САЙТ

Зелёная отметка Deploy сама по себе не подтверждает работу всего приложения.
Я проверю на опубликованном адресе:
• открытие сайта и загрузку иллюстраций на компьютере и в мобильном размере;
• вход сотрудника, преподавателя и администратора, разграничение прав;
• курс → урок → тест → прогресс → сертификат;
• черновик практики → отправку → оценку преподавателя;
• заметки, закладки, уведомления и CSV-отчёт;
• выход, повторный вход и сохранение данных после нового deployment;
• отсутствие ошибок в журнале функций Vercel и корректные записи в Neon.

Ты откроешь ссылку на своём компьютере и телефоне и проверишь удобство.
admin / admin оставляем для локального просмотра по твоему пожеланию.
Для публичного размещения подготовим отдельный пароль администратора;
если нужен свободный показ комиссии, согласуем отдельный демонстрационный вход.

8. ЕСЛИ ЧТО-ТО НЕ ЗАПУСТИЛОСЬ

Ошибка базы / 500:
  Проверяем DATABASE_URL, выбранную ветку Neon, применение схемы и журналы
  Vercel Functions. Строку с паролем не копируем в публичный отчёт об ошибке.

Вход не сохраняется:
  Проверяем HTTPS, cookie, точный домен и PUBLIC_ORIGIN; затем новый deployment.

403 при сохранении:
  Проверяем совпадение Origin с настроенным доменом.

404 на /api/...:
  Проверяем Root Directory, наличие обработчика API и маршруты vercel.json.

Ошибка отсутствующей команды build:
  Сверяем настройки Vercel с фактическим package.json подготовленной версии.

Страницы видны, данные не меняются:
  Проверяем ответы API и подключение к Neon. Одна статическая публикация
  public/ не является полноценной публикацией нашего приложения.

9. КАК БУДЕМ ОБНОВЛЯТЬ САЙТ

После подключения GitHub изменения в production-ветке запускают новый
deployment Vercel. Перед отправкой я проверяю затронутые сценарии. Изменения
схемы базы применяются отдельной миграцией с резервной копией и совместимостью
с текущей версией API. Откат кода Vercel не откатывает данные Neon.
Источник: https://vercel.com/docs/git

После успешного перехода обновлю ВКР: PostgreSQL вместо SQLite, архитектуру,
настройки размещения, адрес и результаты реальной проверки опубликованного
сайта. Скриншоты интерфейса заменим там, где изменится видимое поведение.
